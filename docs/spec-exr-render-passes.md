# OpenEXR render passes

Status: **phases 1 to 4 built and merged** (2026-09-14, branch `exr`;
merged into `v26.3` for 26.3): the
beauty opens through `heeler_io::exr_passes`, a file's Z or mist pass
is the depth map every depth tool reads with the model never running
for it, the Object Mask layer reads Cryptomatte objects and plain
matte channels by name or by clicking them, and Depth Lighting shades
with the render's own normals when the file says which way its camera
faces or the user says the pass is camera space. Phase 5 of 26.3 adds
the writers: 32-bit float TIFF, layered EXR export with the graph's
Export Layer nodes (Phase 8's rename of the Export Channel) as named
layers, and Output's wired alpha. Phase 6
extends the same idea to TIFF on input: a multi-page file reports its
pages to the File node's Layer field, its first page's alpha reads as
the Object Mask's plain channel Alpha and as the File node's mask
output, and a layer editor's private layer stack is reported but not read. Not yet exercised in the running app; the tests are unit
and component level. The once-paused item (Depth Lighting halos on
measured planes, docs/depth-lighting-measured-planes.md) was built on
2026-09-19 on branch `measured-planes`.

## Why

Slider-based RAW editors cannot open an EXR. People who finish still renders
(product, architectural, look development, 3D art) therefore finish
them in a layer editor or a compositor, and a sequence compositor is more tool
than a still needs. Heeler's depth sections (Fog, Depth Lighting, Depth
of Field, Flare, Depth Map) were built to estimate what a render
carries as ground truth: Z depth, surface normals, and per-object
mattes. Reading those passes turns the estimate into the real thing
and gives a second audience a reason to choose Heeler that no photo
editor offers.

A single-part RGB EXR alone is not worth supporting: a 32-bit float
TIFF carries the same pixels. The passes are the feature. 2026-09-14:
"Otherwise why support EXR? Might as well tell people to bake it to
TIFF."

## What was verified on 2026-09-14

- **The `exr` crate (1.74.2, BSD-3-Clause, pure Rust) is already in
  `Cargo.lock`** as the `image` crate's EXR backend, since heeler-io
  builds `image` with default features. No new C library, no new
  license surface. It will become a direct dependency of heeler-io so
  the reader can see every channel.
- **The `image` crate path is not usable for passes.** It looks for
  bare `R`, `G`, `B` channels in the first layer and refuses anything
  else ("image does not contain non-deep rgb channels" on a 3D suite's
  multilayer file), and when it does succeed it drops every channel past
  the fourth. Heeler's generic decoder then runs `input_color::ingest`,
  which applies the sRGB curve to untagged input; an EXR is already
  scene-linear, so a plain RGB EXR opened through today's code would be
  double-linearized. The reader must bypass `ingest` the way
  `decode_png_raw` does.
- **A scratch tool on the `exr` crate read every sample below**:
  headers, layered channel names, the Cryptomatte manifest in the
  header, pixel data, and a correct anti-aliased object matte.

Three renderers, three channel naming conventions:

| Writer | Beauty | Cryptomatte rank 0 |
|---|---|---|
| the 3D suite (our fixture) | `ViewLayer.Combined.R` | `ViewLayer.CryptoObject00.r` |
| production renderer via compositor | (absent) | `uCryptoObject00.red` |
| architectural renderer | `R` | `uCryptoWildcard00.R` |

The reader locates a Cryptomatte by the `cryptomatte/<id>/name` header
attribute and matches channel suffixes case-insensitively with the
long-name aliases (`r`/`red`, `g`/`green`, `b`/`blue`, `a`/`alpha`).
Beauty is found by rule, below.

### Color and range facts

- The 3D suite writes no `chromaticities`; its scene-linear default is
  Rec.709 primaries, which is Heeler's working space, so the beauty
  needs no matrix.
- Combined values run above 1.0 (2.98 peak in the fixture), so intake
  must land exposure the way the DNG bake does with `unbake`, not clamp.
- `Depth.Z` is metric distance with the background at 1e10; `Mist.Z` is
  already 0..1 farness, which is Heeler's own depth convention.
- The 3D suite's Normal pass is **world space** (the ground plane reads pure
  +Z). Heeler's Depth Lighting wants a camera-space normal with +z
  toward the viewer and y down in image space. The architectural renderer writes a
  `cameraTransform` header; the 3D suite writes none. See Normals below.

## Reader design (`crates/heeler-io/src/exr_passes.rs`)

Direct `exr` dependency. One entry, `decode_exr(path) -> ExrImage`,
called from the decode dispatch before the generic `image` path when
the extension is `exr`.

```
ExrImage {
    beauty: ImageBuf,            // RGBA f32, scene-linear sRGB primaries, display-window size
    depth: Option<DepthPass>,    // farness 0..1 at beauty size, plus the raw metric plane
    normals: Option<Vec<[f32; 3]>>, // camera space, Heeler convention, or None
    mattes: Vec<Matte>,          // named 0..1 planes: Cryptomatte objects/materials and plain matte channels
    primaries: Primaries,        // what the beauty was converted from, for the info panel
}
```

**Part and beauty selection.** Single-part files use their one header.
Multi-part files use the first part whose `view` matches the default
view (the first name in the `multiView` attribute) or, absent views,
part 0; the Beachball README documents that part 0 carries the default
channels of the default view. Within the chosen part, beauty is the
first of: bare `R`,`G`,`B`; a layer named `Combined`, `beauty`, `rgba`
or `RGBA`; the first layer with `R`,`G`,`B` children; a bare `Y`
luminance channel. Bare `A` or the layer's `A` becomes alpha, else 1.0.
A file with no beauty at all (the bunny) opens as a neutral gray plate
with its mattes listed, so the mattes are still usable on a File-node
composite, and the info panel says why.

**Windows.** Pixels land in the display window; the data window is
placed at its offset and the rest is zero with alpha 0. Parts with
different data windows are placed independently.

**Primaries.** If `chromaticities` is present and differs from
Rec.709 within tolerance, build the RGB-to-XYZ matrix from the
chromaticities and multiply by `WORKING_SPACE.xyz_d65_to_rgb`, with a
Bradford adaptation when the white differs from D65. ACES2065-1 (AP0,
white 0.32168/0.33767) and ACEScg (AP1, same white) come out of that
same arithmetic. Absent the attribute, assume Rec.709, which is what
the 3D suite, the layer editors and every HDR merger write. A per-photo
override (Rec.709, ACEScg, ACES2065-1, Rec.2020) belongs in the same
place a profile choice for an untagged TIFF would, and is second-phase.
There is no primaries toolkit in the tree today; the closest is the
private 3x3 set in `dng_jxl.rs`, which this work lifts into
`input_color`.

**Exposure.** Beauty is not clamped and not scaled. A render's
highlights above 1.0 are the same headroom a RAW develop carries and
the tone profile's shoulder rolls them off; the 3D suite fixture peaks
near 3.0 and lands fine. An environment map at 1e4 will open bright and
the Exposure control is the answer, as in any HDR editor. An automatic
landing (the `bake::linear_headroom` figure as an initial exposure)
stays an option if real files ask for it.

**Depth.** `Z`, `Depth.Z`, `depth.Z` or `*.Z` in that order, or `Mist.Z`
if present and no Z. Metric Z converts to farness by inverse depth
normalized over the finite range, with the background (non-finite or
above 1e9) pinned to 1.0. Mist is used as is. The raw metric plane is
kept for a later metric-aware Depth of Field.

**Normals.** `Normal.X/Y/Z`, `N.x/y/z`, `normal.R/G/B`. If the header
carries a camera matrix (the architectural renderer's `cameraTransform`, or the 3D suite's none),
rotate world to camera; otherwise treat as camera space and let the
user flip with a "normals are world space" toggle, which is the honest
fallback until the 3D suite writes the matrix. Then convert to Heeler's
convention (flip y, ensure +z toward viewer).

**Mattes.** Two sources, one representation (`Matte { name, plane }`):

1. Cryptomatte. For each `cryptomatte/<id>/name` attribute, parse the
   `manifest` JSON (or the `manif_file` sidecar name, unread in the
   first cut and reported), find the rank channels `<name>NN.{r,g,b,a}`
   for NN = 00.., and expose every manifest entry as a matte. Coverage
   for an object is the sum over ranks of the coverage where the id
   float's bits equal the object's hash. Verified on the fixture:
   Suzanne 28,192 pixels touched, 26,715 fully covered, anti-aliased
   edges intact. Materials come the same way from the CryptoMaterial
   layer.
2. Plain channels. Any single float channel that is not beauty, depth,
   normal, Cryptomatte, disparity or motion (`forward.*`, `disparity*`)
   is offered by name (`whitebarmask.mask` in the Beachball).

Mattes are computed lazily per name and cached under the photo like
smart rasters, keyed by file identity and name.

## Integration points

From the plumbing survey of 2026-09-14 (line numbers of that day):

- **Registration.** Add `exr` to `SUPPORTED_EXTENSIONS`
  (`crates/heeler-catalog/src/lib.rs:194`) and the File-node picker
  (`apps/heeler-app/src-tauri/src/lib.rs:10700`). Leave `RAW_EXTENSIONS`
  alone so the parity test at `crates/heeler-io/src/lib.rs:905` stays
  green.
- **Decode.** Dispatch by extension ahead of `decode_samples`
  (`crates/heeler-io/src/lib.rs:134`); never call `ingest`. The
  auxiliary passes ride beside the `ImageBuf` the way `baked_exposure`
  rides beside a JPEG XL DNG.
- **Depth source.** The one switch point is the `None` arm of the
  `depth_map` command (`apps/heeler-app/src-tauri/src/lib.rs:3827`):
  when the photo carries a depth pass, write its farness plane through
  the same `encode_png16_raw` container instead of running Depth
  Anything. Fold the file identity into `depth_version` (`:3124`) so a
  re-render invalidates the cache. Levels, Edges, Flatten, the picker,
  the histogram, export re-refinement and every consumer follow
  unchanged, because they all read the cached plane. Recompute and
  Detail size are meaningless for a file plane; the Depth block shows
  "From file" in their place, with a way back to the model for
  comparison.
- **Normals.** A second planted slot `{id}@normal` alongside
  `{id}@depth` (`crates/heeler-engine/src/executor.rs:93` and `:476`),
  consumed at the normal construction in
  `crates/heeler-engine/src/ops_depth.rs:740`. The depth plane is still
  needed there for emphasis, lamp z and the silhouette pass; normals
  add to it, they do not replace it.
- **Mattes as masks.** `MaskBuf` is a single 0..1 channel, so a matte
  is already a mask. A new mask source `Object` joins
  `LAYER_MASK_NODE` (`apps/heeler-app/src/state.ts:3953`) as node
  `heeler.matte_mask` with params `source` (object | material |
  channel), `names` (list), `invert`; the desktop plants the coverage
  plane like a smart mask (`plant_smart_rasters_whole`, `lib.rs:1779`).
  The existing Depth block multiplies it like any other mask, so
  "this object, only the near half of it" costs nothing extra.
- **Click to pick.** The Selection tool's picker resolves a click to
  the object under it by reading the rank-0 id at that pixel and
  looking the hash up in the manifest, then adds that name to the
  layer's mask. This is the compositor workflow and it is instant, no model.
- **Formats shown to users.** `docs/user-guide/library.md`, the File-node
  picker filter.

## What the mattes give the user

- Pick "SphereRed" from a list, or click it, and every adjustment on
  that layer (Recolor, Levels, Depth Lighting, Isolate) applies to the
  sphere and nothing else, with the renderer's own anti-aliased edge.
- Materials as well as objects: "all the chrome" in one pick.
- Combine with the Depth block: the sphere, but fading with distance.
- Combine with Fog and Depth of Field driven by the real Z: background
  objects blur by measured distance rather than an estimate.
- Relight one object with Depth Lighting using its true normals.
- Nothing is written back to the EXR. Passes are read-only inputs.

## Phases

1. **Beauty intake.** DONE 2026-09-14. Direct `exr` dependency,
   `exr_passes.rs` with `inspect`, `read_planes` (block-level, only the
   channels asked for are allocated) and `decode_beauty`; part and
   beauty rules, windows, primaries from chromaticities through the new
   `Primaries` toolkit in `input_color` (Bradford to D65, identity for
   Rec. 709); `exr` in the catalog list and the picker; docs and the
   open-source notice. Tests write layered files with the crate itself
   (the 3D suite's naming, inset data window, ACEScg chromaticities, bare RGB,
   luminance, passes only) and, with `HEELER_EXR_SAMPLES` pointing at a
   folder, check the fixture and the downloaded samples.
   `cargo run -p heeler-io --example exr_inspect -- FILE.exr --decode`
   prints what Heeler sees in a file.
2. **Depth from file.** DONE 2026-09-14. `file_depth_source` in the
   desktop crate says whether the photograph's file carries a pass;
   the `depth_map` command reads it through `read_planes_file` and
   `exr_passes::farness` (inverse metric depth normalized over the
   finite range, background pinned far; mist clamped) in place of the
   model, at the preview's size, and the export refinement reads it
   again at the export's own size, so no stretched preview plane ever
   reaches an export. Cache rasters keep their versions; a session
   stamp map (`image_id|version` to file size and mtime) makes a
   re-rendered file a re-read, and the first ask after launch re-reads
   too. The Depth Map section shows a FROM FILE chip in Detail's place
   (the `depth_source` command, asked once per photograph by the
   runner and written to state only when there is a pass) and
   Recompute re-reads the pass. The model's install gate does not
   apply to such a photograph.
3. **Mattes.** DONE 2026-09-14. `heeler.matte_mask` (label Object
   Mask): params `layer` and `names` (JSON list) as the recipe,
   Feather, Invert and the Depth block; the engine op serves the
   planted coverage resampled with no threshold, since partial cover
   is the anti-aliased edge. The desktop plants it like a smart raster
   but computes it in place from the file (`matte_compute`, preview
   tier, persisted under a version that folds in the recipe and the
   file's stamp) and re-reads it at the export's own size
   (`mattes_for_export`). `file_passes` reports the depth channel, the
   Cryptomatte layers with their names and the plain channels once per
   photograph; `matte_pick` names the object under a click. The Object
   layer kind sits beside Smart in the Layers row and the Layer menu;
   its panel lists the file's names by source (Object, Material,
   Channel) with a filter past eight names, chosen names as chips, and
   the `object` viewer tool adds by click and removes by ALT-click. A
   photograph whose file names nothing says so in the panel and
   renders the mask empty. Bunny and Cornell box read through the
   heeler-io tests.
4. **Normals.** DONE 2026-09-14. `inspect` reads the camera out of
   the architectural renderer's `cameraTransform` or the production renderer's `worldToCamera` as a world to
   camera rotation; `camera_normals` turns the pass into unit vectors
   in the lighting convention (y down, z toward the viewer). Depth
   Lighting's `normals` choice (auto, camera, off) decides: auto plants
   only when the camera is known, camera takes the pass as camera
   space, off never. The desktop plants `{id}@normal` (16-bit PNG,
   packed (n + 1) / 2) beside the depth slot, re-reads it at the
   export's size, and the executor injects it as the op's `normal`
   input, which replaces the depth-derived normal wherever the pass
   has one and falls back where it does not. The section shows the
   choice only for a file with a pass, and NO CAMERA IN THE FILE when
   auto has nothing to use (the 3D suite). Follow-up worth its own day: fit
   the camera rotation from the Z and normals passes so the 3D suite's files
   need no toggle.
5. **Float export**, later and separately: an EXR writer beside
   `encode_dng` in `bake.rs`, single-part RGBA half or float. Not part
   of this branch unless asked.

## Known problem: Depth Lighting on the exact plane

the owner's first run (2026-09-14) showed halos and a flat sphere under Depth
Lighting with the fixture's Z pass. Diagnosed in
docs/depth-lighting-measured-planes.md and built 2026-09-19 on branch
`measured-planes`: the key light's cliff band, reduced grid and ripple
gate are tuned for the model's soft map and misread an exact one, so
the op now has a measured-plane contract the desktop selects for a
file's own pass (Edges and Flatten at zero), with the model path
byte-identical to before.

## Review, 2026-09-19

A peer review of the reader, the desktop planting and the frontend
(fourteen findings) was worked through on branch `exr-review`. Fixed:
every flat part of a multi-part file is described and readable, with
part names as layer prefixes; subsampled channels refused by name;
block lengths checked before slicing; a color layer's R, G, B kept
off the matte list; the beauty's alpha offered as a matte; the depth
plane's version folds the file's stamp; a photo switch mid-ask no
longer loses the file_passes answer; the writer refuses non-Latin-1
names, uses ZIP16 scanlines, writes Heeler's farness as `mist.Z`, and
suffixes a duplicate layer name; `manif_file` sidecars are read; the
matte and pick index by the planes' own length; a white point at
y = 0 falls back to D65; the architectural renderer's normals layer is recognized.

Open, recorded rather than fixed: every plane read decompresses the
whole part (one read per file per tier, and a cached rank-0 pair for
the pick, would cut the cost on 140-channel files); the camera-space
handedness of `camera_normals` is verified only on a synthetic
matrix, never on a production renderer's `N` pass with `worldToCamera`; derived
buffers (normals, matte output, plane raster) are not admitted to the
memory budget beyond the planes they are built from; a U32 object-id
pass reads numerically and clamps.

## Decisions for the owner

- **Default primaries** for an untagged EXR: Rec.709 (recommended, it is
  what every still-image writer produces).
- **Where the object list lives**: decided 2026-09-19. In the layer
  mask picker, first in the row, and only for a photograph whose file
  names objects; the panel is a scrollable list with a filter.
- **Normals without a camera matrix**: a per-photo toggle
  (recommended) versus refusing the pass.
- **Float export**: in scope for this branch or not.
