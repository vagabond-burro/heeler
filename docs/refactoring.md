# Refactoring, one small piece per release

The owner's rule, 2026-10-03: "On each release I want an agent to find a small part of the code base and assess it for scalability and identify opportunities for refactoring. I want to keep each scoped down small so the potential ripple effect on introducing bugs is minimal. Every change should be 100% backed up by unit tests. Over time, as features and bugs are addressed the overall code quality is being addressed to avoid accumulation of tech debt."

Tests catch a regression; they do not stop a file from growing into something nobody can change safely. This is the practice that works on that directly, a little at a time, so no release ever needs a rewrite.

## The rule

Every release, update or patch, carries one refactor, and only one: the code base is improved a piece at a time, not all at once (the owner, 2026-10-03: "we don't need to refactor all the code now"). It is done by an agent from the standing prompt, [refactor-prompt.md](refactor-prompt.md), given a final, critical review by a second reader before it lands (the test commits are checked out against the old code to see them pass, and a piece whose tests changed their expectations in the refactor commit is sent back), and recorded in the ledger below.

1. **One target, small.** One concern in one place: a family of functions, a duplicated routine, a module that wants to leave a large file. About 400 changed lines at most, tests not counted, in one crate or one frontend area. If the right fix is bigger, the release does its first safe slice and the ledger says what is left.
2. **Chosen on evidence.** The target is where the release's own work hurt: code that bred a bug, was copied instead of shared, needed the same fix in several places, or could not be tested without the whole app. Size alone is not a reason.
3. **Judged for what comes next.** The question is scalability: what happens to this code when the next feature of its kind arrives. A refactor that only moves text earns nothing.
4. **No behavior change.** Same pictures, same files on disk, same saved numbers, same UI. The goldens do not move. A bug found on the way is fixed in its own commit with its own test, never folded in.
5. **Tests first, in their own commit.** Every line the refactor will touch is exercised by a test that passes on the code as it stands. Where coverage is missing, the tests are written first and committed green against the old code. That commit is the proof.
6. **Then the refactor, with the tests untouched.** The second commit changes the code and leaves those tests' assertions alone (a moved import or a renamed call is fine). If a test has to change its expectation, the behavior changed, and that is not a refactor.
7. **Verified by unit tests, all of it.** The owner, 2026-10-03: "The changes should be 100% verifiable through unit tests. On corner cases, which I think is highly unlikely, they should be identified as must-haves for human testing with explicit guidance on how to test and what to look for." So every changed line is proven by a test that runs in the suites. Where something truly cannot be (how a thing looks or behaves only in the native app), it is not waved through: the report lists it under "Must-have human tests", each with the exact steps, what to look for, and what a failure looks like. That list is expected to be empty; an entry is the exception and needs its reason.
8. **Timing.** After the release's features and fixes have been reviewed, before the cross-platform test runs, and never at the same time as another agent is working in the same files.

## What does not count

- Reformatting, renaming for taste, or reordering.
- Changing a serialized format, a saved key, or an engine op's arithmetic.
- A change whose tests were written after it.
- Anything that needs a migration.

## Candidates

Starting points with evidence, three at most. A release's agent may pick one of these or a better one it finds; a candidate that is done or no longer true is removed. The 26.4.1 report (in git history at 8aad7f31) lists fourteen more families that could leave `lib.rs`, `state.ts` and `simple.tsx`.

- **The wire a picture leaves a node by** (`apps/heeler-app/src/state.ts`). The reducer finds it with a first-match search written by hand wherever it is needed (the file has thirty-five `wires.find` calls, and the ten or so that mean "the wire out of this node" each spell it their own way). In 26.4.0 a second image wire out of a node (an export tap) sent a new layer down the wrong one; 26.4.1 fixed the layer finders and now keeps taps last in the list as a guard. One helper that answers "the chain's wire out of this node" would remove the class of bug and the need for the guard.
- **TIFF directory readers in `crates/heeler-io`**. Five hand-written readers of the same structure: `bake.rs`, `raw_preview.rs`, `dng_jxl.rs`, `exif.rs`, and since 26.4.1 `dng_gain.rs`, which could reuse one only by opening it to the crate. One reader would have made the phone DNG work shorter and would make the next DNG tag a one-line read.
